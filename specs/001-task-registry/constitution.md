# Конституція проєкту: Реєстр задач (Task Registry Service)

## Призначення
Цей документ фіксує непорушні принципи та технічні обмеження проєкту. Будь-які зміни в коді, специфікаціях чи задачах мають безумовно відповідати цим правилам.

---

### Принцип 1. Безпека та секрети (Secrets & Security)
- Жодні API-ключі, токени чи чутливі конфігурації не повинні потрапляти у Git-репозиторій.
- Усі секрети читаються виключно зі змінних оточення (`.env` не відстежується Git).
- У логах сервісу та відповідях API заборонено виводити повні значення ключів доступу.

### Принцип 2. Виключно синтетичні дані (Synthetic Data Only)
- Усі приклади, тестові сценарії та документація використовують виключно вигадані (синтетичні) імена та дані.
- Жодних реальних контактів, прізвищ чи корпоративних відомостей.

### Принцип 3. Непорушність та ізольованість ручного шляху (Manual Path Invariance)
- Ручне створення задач (`POST /tasks`) та отримання списку (`GET /tasks`) є критично важливими бізнес-функціями.
- Вони **ніколи** не повинні залежати від стану, мережевої доступності, лімітів чи збоїв сторонніх LLM-провайдерів.
- Збій AI-модуля не впливає на стабільність базового HTTP-сервісу.

### Принцип 4. Нульова сліпа довіра до LLM (Application Policy Enforcement)
- Відповідь від мовної моделі розглядається як потенційно ненадійний вхідний кандидат (`untrusted proposal`).
- Модель **не має права** самостійно записувати дані в базу даних чи ухвалювати рішення про валідність.
- Застосунок зобов'язаний виконати:
  1. **Структурну валідацію** (відповідність схемі, типи полів, непорожність).
  2. **Змістовну валідацію (Grounding Check)**: відповідальний (`assignee`) та строк (`due_date`) мають бути підтверджені вхідним текстом. Галюцинації (вигадані імена або випадкові дати) негайно відхиляються.

### Принцип 5. Захист сховища даних (State Protection)
- У разі неповного входу, суперечності у тексті, структурної помилки або галюцинації моделі сервіс повертає визначену помилку/уточнення (`needs_clarification` або `invalid_semantics`) і **не змінює стан сховища**.
- Заборонено створювати «напівзаповнені» або пошкоджені записи при відмові.

### Принцип 6. Детермінованість та автономна відтворюваність (Deterministic Testability)
- Усі автоматичні тести (unit, integration, mutation) та основний цикл HTTP-перевірки повинні виконуватися детерміновано без обов'язкового виклику платного зовнішнього API.
- Живий виклик провайдера підтримується, але його недоступність чесно маркується як `not_run`, не блокуючи оцінювання детермінованого ядра.
