# Специфікація продукту: Локальний сервіс реєстру задач

**Версія:** 1.0.0  
**Автор / Роль:** Product Manager (PM)  
**Статус:** Схвалено для розробки  
**Базова функція:** 001-task-registry  

---

## 1. Проблема та бізнес-цінність

### 1.1. Проблема
Після нарад та зустрічей домовленості фіксуються у чатах чи нотатках у вільному текстовому вигляді. Домовленості часто губляться, відповідальні особи не фіксуються, або виникає непорозуміння щодо строків виконання.

### 1.2. Ціль
Створити локальний HTTP-сервіс, який дозволяє надійно вести реєстр задач як вручну, так і автоматично видобувати структуровані задачі з тексту повідомлень після зустрічей за допомогою LLM із **гарантованим захистом від вигаданих зобов'язань (галюцинацій)**.

---

## 2. Користувацькі історії (User Stories)

- **US-1 (Ручне створення):** Як член команди, я хочу надіслати валідний JSON із полями задачі через HTTP API, щоб зафіксувати заплановану роботу в єдиному реєстрі.
- **US-2 (Перегляд списку):** Як PM або лід команди, я хочу отримати актуальний список усіх збережених задач у форматі JSON, щоб контролювати виконання домовленостей.
- **US-3 (Видобування з тексту):** Як учасник зустрічі, я хочу надіслати вільний текст повідомлення в API, щоб сервіс за допомогою LLM видобув параметри задачі, програмно перевірив їхню присутність у тексті та зберіг задачу лише за повної відповідності вимогам.

---

## 3. Межі продукту (Scope)

### 3.1. Включено в Scope (In-Scope)
1. Локальний сервіс на базі FastAPI.
2. Три ключові операції:
   - `GET /tasks` — отримання списку задач.
   - `POST /tasks` — ручне створення задачі.
   - `POST /tasks/from-text` — створення задачі з тексту з перевіркою LLM-пропозиції.
3. Сутність задачі:
   - `id`: ціле додатне число (автоматично генерується сервісом).
   - `title`: назва задачі (рядок, 3–100 символів).
   - `description`: опис / деталі (рядок, 1–500 символів).
   - `assignee`: відповідальний (рядок, 2–50 символів).
   - `due_date`: строк виконання (рядок у форматі ISO `YYYY-MM-DD`).
4. Політика верифікації (`Application Policy`):
   - Перевірка обов'язкових полів.
   - Захист від галюцинацій (Grounding Check): ім'я `assignee` та дата `due_date` мають бути присутні у вихідному тексті.
   - Захист від суперечностей та неповних даних (повернення статусу `needs_clarification` без створення запису).
5. Ізольоване файлове або in-memory сховище з можливістю скидання для тестів.

### 3.2. Виключено зі Scope (Out-of-Scope)
- Складний графічний UI (достатньо REST API та Swagger/Jupyter).
- Авторизація, аутентифікація, користувацькі сесії.
- Хмарні СУБД (PostgreSQL тощо) чи розподілені черги.
- Автономні мультиагентні цикли, інструменти (Tools/MCP), RAG.
- Відправка повідомлень у сторонні канали (Slack, Email).

## 4. Специфікація API та HTTP Контракти

### 4.1. `GET /tasks`
- **Опис:** Отримання списку всіх зареєстрованих задач.
- **Вхідні дані:** Відсутні.
- **Успішна відповідь:** `HTTP 200 OK`, JSON-масив об'єктів `Task`.
- **Приклад:**
  ```json
  [
    {
      "id": 1,
      "title": "Підготувати звіт",
      "description": "Фінальний звіт релізу",
      "assignee": "Ірина",
      "due_date": "2026-11-20"
    }
  ]
  ```

### 4.2. `POST /tasks` (Ручне створення)
- **Опис:** Створення задачі з явно переданих полів без участі AI.
- **Вхідне тіло (JSON):**
  ```json
  {
    "title": "Підготувати релізний звіт",
    "description": "Звести результати тестування",
    "assignee": "Ірина",
    "due_date": "2026-11-20"
  }
  ```
- **Успішна відповідь:** `HTTP 201 Created`, об'єкт `Task` із присвоєним `id`.
- **Відмова валідації:** `HTTP 422 Unprocessable Entity` (порожні поля, довжина поза межами, некоректний формат дати). Сховище не змінюється.

### 4.3. `POST /tasks/from-text` (Створення з тексту через LLM)
- **Опис:** Перетворення тексту домовленості у задачу за допомогою LLM-пропозиції та програмної політики.
- **Вхідне тіло (JSON):**
  ```json
  {
    "text": "Підготувати звіт; опис: перевірити метрики; відповідальний: Ірина; строк: 2026-11-20"
  }
  ```
- **Сценарій 1 (Успіх):**
  - Статус: `HTTP 201 Created`
  - Тіло: створений об'єкт `Task` із `id` та метаданими `{ "status": "created", "path": "llm" }`.
- **Сценарій 2 (Неповні або суперечливі дані):**
  - Статус: `HTTP 422 Unprocessable Entity`
  - Тіло: `{ "status": "needs_clarification", "reason": "...", "missing_fields": [...] }`.
  - Сховище: **не змінюється**.
- **Сценарій 3 (Структурний збій або галюцинація моделі):**
  - Статус: `HTTP 422 Unprocessable Entity`
  - Тіло: `{ "status": "invalid_semantics", "reason": "Галюцинація: відповідального 'Богдан' немає у вхідному тексті" }`.
  - Сховище: **не змінюється**.
- **Сценарій 4 (Збій провайдера моделі):**
  - Статус: `HTTP 503 Service Unavailable`
  - Тіло: `{ "status": "provider_unavailable", "reason": "Збій звернення до моделі" }`.
  - Сховище: **не змінюється**, наступні запити до `GET /tasks` та ручного `POST /tasks` виконуються штатно.

## 5. Критерії приймання (Acceptance Criteria)

- **AC-1 (Перегляд списку):**  
  Запит `GET /tasks` повертає HTTP 200 та список задач у вигляді JSON-масиву. Усі збережені задачі повертаються без втрати або модифікації полів.

- **AC-2 (Ручне створення):**  
  Запит `POST /tasks` з коректними даними створює рівно один новий запис, повертає HTTP 201 та згенерований `id`. Кількість записів збільшується рівно на один; попередні записи залишаються незмінними.

- **AC-3 (Захист від некоректного ручного входу):**  
  Запит `POST /tasks` із некоректними даними (наприклад, порожній заголовок, відсутній виконавець, хибний формат дати) повертає HTTP 422. Сховище не змінюється (ідентифікатори та поля попередніх записів ідентичні до і після запиту).

- **AC-4 (AI-видобування та Grounding):**  
  Запит `POST /tasks/from-text` для однозначного тексту створює задачу з HTTP 201. Якщо у тексті бракує відповідального чи дати, текст суперечливий, або модель повернула галюцинацію (вигадане ім'я/дату) — сервіс повертає HTTP 422, а сховище не зазнає жодних змін.

- **AC-5 (Стійкість до збоїв провайдера):**  
  У разі збою зовнішнього провайдера моделі `POST /tasks/from-text` повертає HTTP 503 без аварійного завершення процесу. Ручні операції `GET /tasks` та `POST /tasks` зберігають 100% працездатність.

## 7. Розділ «Уточнення» (Clarifications & Decisions)

Специфікація була надана незалежному рецензенту (незалежний читач без доступу до коду). Зафіксовано такі запитання та офіційні рішення PM:

1. **Питання 1:** Що робити, якщо повідомлення містить два імені, наприклад: «Ірина або Максим мають оновити реліз»?  
   - **Рішення PM:** Система не має вгадувати виконавця. Повертати HTTP 422 зі статусом `needs_clarification`. Запис у базу не додається.  
   - **Відповідальний:** PM.

2. **Питання 2:** Як трактувати дату, якщо в тексті замість ISO формату зазначено «до кінця тижня»?  
   - **Рішення PM:** У базовій версії сервісу (до прийняття окремого запиту на зміну) приймаються виключно точні дати у форматі ISO `YYYY-MM-DD`. Відносні формулювання повертають статус `needs_clarification`.  
   - **Відповідальний:** PM.

3. **Питання 3:** Чому статус помилки для `needs_clarification` та `invalid_semantics` обрано саме HTTP 422, а не HTTP 200 з прапорцем?  
   - **Рішення PM:** Для створення ресурсу клієнт очікує успішний результат створення (201). Повернення 200 при невдалому видобуванні може ввести клієнта в оману (silent failure). HTTP 422 (Unprocessable Entity) чітко сигналізує, що синтаксис запиту правильний, але семантичний зміст не дозволяє створити сутність.  
   - **Відповідальний:** PM / Tech Lead.

4. **Питання 4:** Чи допустима зміна кількості записів у сховищі, якщо модель створила порожню або дефектну задачу?  
   - **Рішення PM:** Категорично ні. Будь-який неуспішний результат повинен залишати сховище ідентичним за ідентифікаторами та полями (перевіряється через `snapshot(before) == snapshot(after)`).  
   - **Відповідальний:** QA Lead / PM.
