# Специфікація запиту на зміну (Change Request Spec)

**Код запиту:** CR-001  
**Тема:** Автоматичне встановлення найближчої п’ятниці за відсутності строку в тексті  
**Ініціатор:** Замовник  
**Роль рецензента та автора:** Product Manager (PM)  
**Статус:** СХВАЛЕНО З УТОЧНЕННЯМ  

---

## 1. Запит замовника та бізнес-контекст
> «Якщо строк не зазначено у тексті повідомлення після зустрічі, автоматично ставте найближчу п’ятницю».

### Оцінка ризиків та користі:
1. **Користь:** Зменшує кількість блокувань (`needs_clarification`) для типових задач, які команда за замовчуванням бере у тижневий спринт.
2. **Ризик вигаданого зобов'язання (Phantom Commitment):** Якщо дата не узгоджена на зустрічі, штучне призначення дедлайну може призвести до штрафів або хибної звітності.
3. **Ризик невизначеності «найближчої п'ятниці»:** Якщо повідомлення надіслано в п'ятницю о 17:00, встановлення дедлайну «на сьогодні» є абсурдним.
4. **Рішення PM:**  
   Прийняти запит **з обов'язковими обмеженнями**:
   - Розрахунок виконується виключно детермінованим кодом застосунку, а не мовною моделлю!
   - Повідомлення клієнту містить явне попередження (`auto_due_date: true`, `notice: "..."`).
   - Якщо сьогодні п'ятниця — призначати п'ятницю наступного тижня (+7 днів).

---

## 2. Алгоритм розрахунку «найближчої п'ятниці»

- Опорна дата: `today` (за замовчуванням поточна системна дата або параметр тестового середовища).
- День тижня: понеділок = 0, вівторок = 1, середа = 2, четвер = 3, п'ятниця = 4, субота = 5, неділя = 6.
- Правило:
  - Якщо `weekday` в діапазоні `0..3` (Пн–Чт): `delta_days = 4 - weekday` (п'ятниця цього тижня).
  - Якщо `weekday == 4` (Пт): `delta_days = 7` (п'ятниця наступного тижня, оскільки дедлайн «на сьогодні» не встановлюється).
  - Якщо `weekday` в діапазоні `5..6` (Сб–Нд): `delta_days = (4 - weekday) + 7` (п'ятниця наступного тижня).

## 3. Зміни в контрактах та поведінці API

### 3.1. `POST /tasks/from-text`
1. **Якщо дату вказано в тексті:** Працює базове правило (AC-4a). Дата перевіряється на присутність у тексті. Поле `auto_due_date = false`.
2. **Якщо дату НЕ вказано, але виконавець та назва присутні:**
   - Модель повертає `due_date: null` (згідно з промптом B).
   - Сервіс обчислює дату найближчої п'ятниці за алгоритмом.
   - Створюється задача з обчисленою датою.
   - Відповідь HTTP 201 додатково містить:
     ```json
     {
       "id": 2,
       "title": "Оновити залежності",
       "description": "безпекові патчі",
       "assignee": "Олексій",
       "due_date": "2026-11-13",
       "auto_due_date": true,
       "notice": "Строк не було вказано; автоматично встановлено найближчу п'ятницю: 2026-11-13",
       "status": "created",
       "path": "llm"
     }
     ```
3. **Якщо відсутній виконавець:** Сервіс, як і раніше, повертає `HTTP 422 needs_clarification` (відсутність виконавця ніколи не підставляється автоматично!).

### 3.2. Ручне створення `POST /tasks`
- **БЕЗ ЗМІН (Регресійний захист):** Обов'язкова явна передача поля `due_date`. Відсутність дати в ручному запиті повертає `HTTP 422`.

---

## 4. Оновлені критерії приймання

- **AC-4a (Базове видобування з явною датою):**  
  Текст із явною датою створює задачу з цією датою; `auto_due_date == false`.
- **AC-4b (Автопідстановка найближчої п'ятниці):**  
  Текст без зазначеного строку, але з валідним виконавцем і назвою створює задачу з датою найближчої п'ятниці; `auto_due_date == true`, присутнє інформативне повідомлення `notice`.
- **Регресійні перевірки:**  
  - AC-1, AC-2, AC-3 залишаються 100% незмінними.
  - Галюцинація виконавця (C7) та відсутність виконавця (C4) як і раніше відхиляються з кодом 422.
